## Вывод 1. Диагностический счётчик sdk_fwd — НЕИСПРАВЕН, результат «sdk_fwd=0» вводит в заблуждение
Проверено по исходникам ядра (build_dir/.../linux-4.14.336/net/ipv4/ip_output.c:390,398):
на NF_INET_POST_ROUTING во ВСЕХ пустях (и для форварда, и для локального трафика) вызов
NF_HOOK идёт с indev=NULL (net, sk, skb, NULL, dev, ...).
=> в хуке bind_hook state->in ВСЕГДА == NULL.
=> ветка `if (state->in)` -> sdk_fwd++ НИКОГДА не выполняется, а ВСЕ записи хука
   (включая форварднутый трафик клиента) учитываются как sdk_local.
=> Вывод «туда (в POSTROUTING) forwarded-трафик не попадает» из более ранних стадий — НЕВЕРЕН.
   Forwarded-трафик попадает в хук (счётчики bind_hook растут), просто диагностика его не различает.
==> Если нужен раздельный учёт: вместо state->in использовать state->out (egress dev).

## Вывод 2. Хэш FOE НЕ коммутативен — код-комментарий «hash is commutative in src/dst ip» опровергнут
Проверено формулой 1-в-1 по mtk_flow_hash_v4_ct(python) на реальных слотах из теста 8:
  t_this ORIG  192.168.3.142:60654 -> 4.207.247.137:443 => slot 0xc64  (СОВПАЛ с наблюдением)
  t_this REPLY 4.207.247.137:443 -> 192.168.2.212:60654 => slot 0xaf0  (СОВПАЛ с наблюдением)
  Проводная post-NAT форма CPU-излучённого кадра 192.168.2.212:60654 -> 4.207.247.137:443
  => slot 0xed0   (!! НЕ равен 0xaf0 и НЕ равен 0xc64)
  Обратный ORIG 4.207.247.137:443 -> 192.168.3.142:60654 => slot 0xc44  (НЕ равен 0xc64)
Из-за множителей (ports&src)|((~ports)&dst) и `ports^src^dst` хэш НЕ симметричен.
## Вывод 3 (следствие): для SNAT-трафика WiFi-клиентов исходящее направление offload-ится «мимо».
PPE видит на проводе post-NAT кадр (wan_ip -> remote_ip) и хэширует его в 0xed0.
bind_hook для ИСХОДЯЩЕГО трафика хэширует t_this = pre-NAT (client_ip -> remote_ip) = 0xc64.
Слот 0xed0 хук никогда не смотрит/не биндит => HW-запись для исходящего направления WiFi-flow
не создаётся (либо создаётся «чужая»/неверная, если туда попадёт другой lookup).
Для проводного клиента (кадра pre-NAT пересекают свитч) симметрия сохраняется и возможно работает.

## Вывод 4. Перелом = момент активации offload (причина инцидента доказана косвенно)
До cd2eb4e: BIND=0 (нет эффективного offload), интернет РАБОТАЛ.
После cd2eb4e+259086c: BIND-записи создаются (13..16, затем 138/50 в бурсте торрента),
интернет СЛОМАН (ICMP жив, TCP дохнет, апстрим-GUI из-под клиента недоступен, торрент без обмена).
=> Поломка происходит именно когда HW (PPE) начинает брать поток на себя, а записи/поведение
   HW-пути для потока некорректны. ICMP никогда не биндится и потому работает.

## Рабочие гипотезы (по убыванию вероятности)
H1. HW offload одного направления биочится в «чужой»/неправильный слот или egress-порт,
    из-за чего кадры реплицируются/поворачиваются внутрь LAN (симптом: «интернета нет, ICMP есть»).
H2. Проблема egress В РЕПЛИ-направлении на WiFi-клиента (nvhw на свитче)
    — СНЯТА: T-A (все тесты 1..10 выполнялись ПО КАБЕЛЮ) показал, что кабельный форвард тоже сломан.
H3. Поток «двойного-форварда» (CPU-клонирование offloaded-кадров) — СНЯТА вместе с H2 (не зависит от egress).
H4. Слоты churn-атся (торрент: BIND->UNBIND массово) + BNDR=1 flutter из старых стадий гоняет CPU.
H5. (маловероятно) FOE-запись заполнена не по правилам конкретной ревизии PPE (64B vs 80B) —
    не подтверждено: даташитовые поля согласуются с кодом, записи выглядят «правильно».
H6. (НОВАЯ, основная) Поломка в ОБЩЕМ RX-пути REPLY-направления после активации BIND:
    T-B2 показал, что даже локальный (не-натированный, dst=сам роутер 192.168.2.212) поток
    теряет ДАННЫЕ reply (0 байт), хотя хэндшейк проходит. Для локального трафика NAT отсутствует,
    поэтому wire-форма кадра = t_this/reply как в CT (исключает «хэширование мимо» из Вывода 3).
    => подозрение на (a) перезапись заголовков данным записи FOE (dmac впиcан MAC клиента, а не CPU)
       => reply «уходит внутрь LAN вместо доставки роутеру/клиенту»; (b) неверный egress-VLAN/порт
       (во всех reply-записях vlan1=0, info1=0x...0b4d); (c) PPE считает запись UNBIND при покадровой
       проверке (растут 0x0e/0x0f несмотря на стабильные BIND в RAM) и применяет rate/drop-политику.

## Анализ по исходникам
1) Software flowtable активна ТОЛЬКО при наличии правила
   `iptables -t raw -A PREROUTING -j FLOWOFFLOAD`,
   которое firewall3/LuCI генерирует из `/etc/config/firewall` `option flow_offloading`.
   Стоковый дефолт — `flow_offloading 0` (package/network/config/firewall/files/firewall.config:7),
   в тестах Luci держался выключенным => flowtable НЕ была активна и не могла ломать связь.
2) Даже если бы была включена: на MT7620 HW-ADD запрещён — fe_flow_offload() возвращает -EINVAL
   для FLOW_OFFLOAD_ADD (mtk_eth_soc.c:1493-1503, коммит de007cf0cc). Т.е. flowtable не может
   создавать FOE-записи state=BIND на MT7620 — разрешён только DEL (чистка) пути.
3) Единственный писатель state=BIND на MT7620 — наш bind-hook (mtk_offload_bind_hook, POSTROUTING).
   Связка «BIND=0 => интернет есть / BIND>0 => интернет сломан» держится без всякого flowtable
   => софт- и сток-хв offload НЕ являются причиной (их выключение в LuCI на исход ничего не меняло).
4) ВТОРИЧНОЕ взаимодействие (не причина, но помнить): если flow_offloading ВКЛЮЧИТЬ —
   flowtable fast-path пускает пакеты мимо POSTROUTING (хук видит меньше трафика),
   а DEL-путь mtk_flow_offload (mtk_offload.c:329-366) трогает SMA PPE и чистит кэш при expiry.
